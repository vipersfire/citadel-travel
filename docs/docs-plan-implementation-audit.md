## Migration behavior

Migrations were exercised only against temporary databases, including a populated baseline with an existing booking, paid invoice and payment attempt. Applied migration files were preserved; the V2 schema was generated with Drizzle and additional data/trigger migrations were added.

On the next normal startup:

- Old sport products return to draft until an administrator verifies or intentionally publishes them as interest-only.
- Old luxury products become archived records with `sport = other`; existing booking and financial references remain intact.
- Public authored pages containing legacy luxury language return to draft for review. Known application-owned seed titles and hero copy receive the V2 names and copy.
- No supplier verification, commercial approval or historical member approval is invented.

Two compatibility differences from the fresh-install DDL are intentional:

- `payment_attempts.approval_id` remains nullable for historical attempts. A database trigger requires a valid approval for every **new** attempt. New payment APIs require the same-version approval and matching total.
- `leads.whatsapp_e164` remains nullable for historical records and account anonymization. Every new public enquiry requires a valid WhatsApp number.

Readiness on newly issued invoices is enforced by a database trigger so existing paid invoices do not need fabricated readiness evidence. Staff should review existing unpaid legacy offers and cancel their old provider links before reissuing through the V2 flow.
